Install Shield Training - Invitation
Thu, Jul 9, 2026

Summary:

The meeting covered hands-on MSI packaging workflows, troubleshooting installer failures, and MSI authoring concepts including custom actions, sequencing, AppSearch, and merge modules. Attendees confirmed using an MSI produced by AdminStudio for exercises because the trial tool on the training VM could not generate the full MSI output from the release wizard.

The team demonstrated the IRP→ISM→MSI workflow and release-wizard options, and reviewed packaging output types (single compressed MSI, uncompressed with external files, and MSI with external CAB), plus the recommendation to create one CAP/CAF per feature to avoid excessive per-component files. SK located a usable MSI in an alternate project output and advised using it for hands-on work until a licensed environment is available.

Installation troubleshooting and logging were demonstrated: building a silent install command, monitoring MSI processes and Event Viewer, enabling Image Path/Command Line in Task Manager, and reading verbose MSI logs to locate return codes and failing actions. A 1603 fatal error was shown and common causes were listed (insufficient privileges, file/AV/GPO blocking, network inaccessibility); elevation of the installer was recommended when privilege issues appear.

MSI authoring topics included execute vs. UI sequences, standard action sequencing and rollback behavior, the importance of not reordering standard actions, and how custom actions must be explicitly scheduled. SK demonstrated the Direct Editor/Install-Seal view to inspect sequence tables, add table entries, and install merge modules; attendees saw how merge modules contribute components and must be integrated into an MSI. AppSearch/System Search usage was shown with examples (registry, file, drive searches) and how results populate MSI properties used in conditions or custom actions.

Constraints and open items: the trial tooling limited saving edits and generating release MSIs, so a licensed Install-Seal/AdminStudio environment is needed to perform full hands-on custom-action exercises; Aman will confirm which MSI will be used for the next session. The instructor recommended practicing capture workflows, verbose-log analysis, and gaining basic PowerShell skills to support packaging tasks.

Reading MSI logs and verifying properties

Directory resolution and variable use

Custom actions, ROOTDRIVE, and troubleshooting
SK covered creating custom actions and warned against hard-coded paths in scripts because they can fail when the OS or Program Files exist on nonstandard drives; he showed how to enforce installation on a specific drive via the ROOTDRIVE property and explained common troubleshooting steps for missing folders, architecture mismatches, and per-user vs. system installs by inspecting the log and component settings.
* Participants were strongly warned not to hard-code paths in custom action scripts and to prefer MSI variables or set a ROOTDRIVE property when clients require a specific installation drive.
* Common installation failures can result from architecture mismatches (template summary or component bitness) or per-user vs system-level installs, and these should be diagnosed via the log.

Locating MSI entries in the log
The instructor walked attendees through using the log viewer and search (control-F) to find MSI filenames and package locations, showing how an extracted MSI appears in the log and explaining that the installer will use that extracted copy during repairs.
* The extracted MSI location in the installer cache is used for repair operations and deleting it can break repair, producing general errors.

Implications of deleting installer cache and repair behavior
The instructor explained that deleting or corrupting the installer cache can prevent repairs and cause general errors. He demonstrated that the installer references the cached MSI for repair operations and recommended verifying the MSI in the cached location when troubleshooting.

Execution sequence and return values
The instructor described MSI execution sequencing: actions (copying files, deleting) run in a defined order from the MSI database and each action returns a value—0 for success and 3 for error—so the log return values identify failing actions. He illustrated using launch condition and property changes as examples.
* MSI actions run in a defined execution sequence and each action returns a value that indicates success (0) or error (3) to help locate failures.

Mapping log names to sequence numbers in the authoring tool
The instructor demonstrated the MSI authoring tool, showing execute and custom-action trees and how logged action names (app search, launch condition, install finalize) map to defined sequence numbers (for example, app search = 400 and install finalize = 6600). This mapping helps correlate log entries to MSI tables for diagnosis.
* Participants were instructed to study "app search" and related MSI topics after the session and may consult the instructor for clarification.
* Logged action names (for example, app search and launch condition) correspond to sequence numbers visible in the MSI authoring tool.

Standard actions, limitations, and custom actions scheduling
The instructor reviewed standard (built-in) MSI actions, noted that not all actions run for every installation scenario, and warned against manually disturbing standard action sequencing. He explained that reserved gaps allow insertion of custom actions, but custom actions must be scheduled explicitly and placed between appropriate standard actions to execute correctly.
* Standard MSI action sequencing includes reserved gaps; custom actions must be explicitly scheduled and can be placed between standard actions without altering the built-in sequence.

Tables, AppSearch, and merge modules
The instructor explained that many MSI tables are blank when not required, pointed out AppSearch may be empty for some MSIs, and walked through adding merge modules from the redistributable view, including the option to download modules from the internet and how adding a module creates component entries and updates module tables for hands-on observation.
* Merge modules can be added from the redistributable view and may be downloadable from the internet; adding them alters component and module tables in the project.

Merge Module behavior and installation constraints
The instructor clarified that Merge Modules (MSM) are a Windows Installer artifact that must be integrated into an MSI to be installed, and that MSMs install their own defined components into their own folders rather than into the primary product folder. The instructor emphasized MSM file naming/extension details and reiterated that MSMs require an MSI wrapper to execute.
* MSMs install their components into their own predefined folders, not into the product's main installation folder.
* Merge Modules (MSM) cannot be installed standalone and must be integrated into an MSI to be applied.
* The lab environment cannot persist or fully demonstrate AppSearch runtime effects without an appropriate MSI/license to run and save results.

Introduction to AppSearch / System Search concept
The session introduced the AppSearch (system search) area of the tool, prompting learners to consider what system search does and confirming it is a pre-install detection mechanism. The instructor asked for ideas from participants and set up the next detailed explanation.

How system searches determine installation conditions
Aman explained that AppSearch searches the target machine and stores results in MSI properties. The instructor expanded with examples: checking Internet Explorer version or presence of specific files (e.g., explorer.exe or VLC.exe) or registry uninstall strings to detect installed applications, and using those results to conditionally install components so only the appropriate DLL/component is installed.
* AppSearch/System Search is used to detect files, registry values, or INI contents on the target machine and store results in MSI properties.

Properties and use of AppSearch results
The instructor demonstrated how system search results populate properties (e.g., "InternetExplorerFound = yes/no") and showed how those properties drive conditions for component installation, launch conditions, and custom actions. The instructor explained default values, property setting based on search results, and reuse of properties across the installer logic.
* Stored AppSearch properties can be used in component conditions, launch conditions, or custom actions to control installation behavior.

Hands-on adding predefined and custom searches
The class practiced adding system searches by right-clicking in the AppSearch area, choosing predefined searches, and walking through the predefined Adobe Reader 11 example that reads InstallPath from the registry and stores it as a property for later use. The instructor also described how to add custom searches (file, registry, drive, INI) and what inputs are required (root hive, registry path, INI section/key).
* The predefined search workflow (example: Adobe Reader 11) reads InstallPath from the registry and sets a property representing that folder for subsequent actions.

Direct Editor verification and lab limitations
Participants were instructed to add a sample registry search and then inspect the AppSearch table in the Direct Editor to confirm a new entry appears. The instructor noted the lab limitation that changes cannot be saved or fully visualized without an appropriate license or MSI to run custom actions, and recommended practicing with a licensed MSI when available.
* Adding a system search creates an AppSearch table entry visible in the Direct Editor, demonstrating the linkage between the UI and MSI tables.
